# /essence — Essence Card 추출

Wiki 페이지를 **AI 에게 지시할 때 꺼내 쓰는 카드**로 압축한다. 목적은 요약이 아니라 **AI 협업 문해력** — 이 개념으로 AI 에게 무엇을 시킬 수 있고, 산출물에서 무엇을 검사하고, 어떤 제약을 반복해서 상기시킬지를 한 화면에 남긴다.

> **핵심 원칙 — 카드는 페이지의 압축이지 보강이 아니다.** 카드의 모든 줄은 페이지 본문의 어느 줄에서 왔는지 가리킬 수 있어야 한다. 페이지에 없는 능력·증상·규칙은 일반 지식으로 아무리 옳아도 쓰지 않는다 — 출처 없는 주장이 Wiki 에 들어가는 통로가 되기 때문이다. 페이지가 부족하면 카드도 짧고, 그 사실을 보고한다.

> **🧭 Prerequisite (옵션)**: 볼트에 사용자 맥락 파일(예: `Core Context.md`)이 있으면 세션당 한 번 먼저 읽는다. 없으면 건너뛴다.

## Input

`$ARGUMENTS`

- Wiki 페이지명 (복수 가능) — 개념·가이드 성격의 `type: wiki-page` (이 볼트 예: `21. Concepts/` · `23. Guides/`)
- MOC 명 — leaf 페이지(Concepts · Guides) 전체를 순회. Raw Source · 하위 MOC · Entities 는 건너뛴다
- `--force` — 이미 `## Essence Card` 가 있는 페이지도 다시 쓴다. 없으면 기존 카드는 **건너뛰고 보고만** 한다
- 인자가 없으면 어느 페이지를 압축할지 한 번 묻는다

## Process

### Step 1: 페이지 읽기 — 재료 표를 먼저 채운다

페이지 전체를 읽고, 쓰기 전에 아래 재료를 **페이지 안에서** 찾아 메모한다. 비어 있으면 비워 둔다 — 채우려고 바깥 지식을 끌어오지 않는다.

| 재료 | 페이지의 어디서 | 카드의 어디로 |
|---|---|---|
| `> [!tip] 한 문장 모델` 의 **실정의** 줄 | 본문 상단 콜아웃 | §1 — **글자 그대로** |
| **비유의 경계** 줄 | 같은 콜아웃 | §3 제약 · §6 |
| 본문이 "할 수 있다 / 해결한다 / 보장한다" 고 말하는 대목, 표의 "쓰기 좋은 곳" 열 | 본문·표 | §2 |
| `> [!warning] 실전 함정` 의 각 불릿 | 콜아웃 | §3 확인 순서 · §4 |
| 본문·`## 교안이 멈춘 곳` 류 섹션의 오류 코드·실패 사례 | 본문 | §4 증상 |
| `related:` 의 페이지 (MOC 제외) | frontmatter | §5 — 정확한 페이지명으로 wikilink |
| `## 육성 인용` 의 강사 강조 | 섹션 | §6 의 문장 어조 |
| `confidence:` · `verificationStatus:` | frontmatter | §6 꼬리표 |

### Step 2: 카드 작성 — 아래 형식 그대로

카드는 페이지 안의 **H2 하나**다. 소제목은 H3, 구분선(`---`)은 넣지 않는다. 본문은 한국어, 코드·식별자·오류 코드는 원어. 각 항목은 한 줄.

````markdown
## Essence Card

### 1. 한 문장 정신 모델

{한 문장 모델의 실정의 줄을 글자 그대로. 굵게 표시도 그대로}

### 2. 이 개념으로 AI 에게 시킬 수 있는 것 · 산출물에서 검사할 수 있는 것

- {페이지가 말하는 능력 1 — "…하게 할 수 있다" 또는 "…인지 검사할 수 있다" 꼴}
- {능력 2}
- {능력 3}

### 3. AI 협업 패턴

**작성 지시**

```text
{개념}을 사용해 {작업}을 만들어줘.

제약:
- {실전 함정 또는 비유의 경계에서 온 제약 1}
- {제약 2}
- {제약 3}
- 수정 후 {이 개념에서 결정한 것}을 한 줄로 설명
```

**오류 수정 지시**

```text
다음 {개념} 오류를 수정해줘.

확인 순서:
1. {§4 레버 1 의 "먼저 확인할 것"}
2. {§4 레버 2 의 "먼저 확인할 것"}
3. {§4 레버 3 의 "먼저 확인할 것"}

수정 시 오류 원인 · 최소 수정안 · 바뀐 {영향 범위} 만 설명.
```

### 4. 문제 해결 레버 (증상 → 먼저 확인할 것)

- **{페이지에 적힌 증상·오류 코드·실패 사례}** → {같은 대목이 지목하는 원인·확인점}
- **{증상 2}** → {레버 2}
- **{증상 3}** → {레버 3}

### 5. 관계

- [[{related 의 정확한 페이지명}]] — {이 페이지와의 관계 한 줄}
- [[{페이지명 2}]] — {관계}

### 6. AI 제약 (반복해서 쓸 문장)

```text
{이 개념의 핵심을 한 문장으로. AI 에게 매번 다시 상기시킬 규칙}
```
{confidence 가 high 가 아니거나 verificationStatus 가 verified 가 아니면 이 줄을 둔다:}
> 출처 페이지 `confidence: {값}` · `verificationStatus: {값}` — 이 제약은 단일 교안 기준이다. AI 가 반박하면 페이지를 다시 확인한다.
````

**각 섹션의 채우기 규칙**

- **§1** — 실정의 줄을 복사한다. 페이지에 `한 문장 모델` 콜아웃이 없으면 본문 첫 정의 문장에서 한 문장을 쓰고, 줄 끝에 `(페이지에 한 문장 모델 없음 — 카드에서 작성)` 을 붙인 뒤 Step 4 보고에 올린다.
- **§2** — 3~5 줄. 사용자가 AI 에게 **지시할 수 있는 일** 또는 AI 산출물에서 **검사할 수 있는 일**로 쓴다. 페이지가 말하는 능력만 쓴다. 3 줄이 안 나오면 있는 만큼 쓰고 보고에 사유를 남긴다.
- **§3** — 제약은 `실전 함정` · `비유의 경계` 에서 온다. **오류 수정 지시의 확인 순서는 §4 의 "먼저 확인할 것" 을 순서대로 번호 붙여 넣은 것이다** — §4 를 먼저 채우고 옮겨 적는다. 이 목록은 비어 있을 수 없다. 실전 함정이 3 개 미만이면 본문의 "…하면 깨진다" 류 문장을 더한다. 그래도 모자라면 모자란 채로 둔다.
- **§4** — 증상은 페이지에 적힌 오류 코드(`TS2339` 등)·실패 사례·"…을 잃는다" 류 표현에서 가져온다. 페이지에 없는 오류 메시지를 일반 지식으로 지어내지 않는다. 3 개 미만이면 있는 만큼.
- **§5** — `related:` 의 항목 중 `MOC-` 로 시작하지 않는 것을 **정확한 파일명**으로 wikilink 한다. 관계 설명은 페이지 본문이 그 개념을 언급한 맥락에서 쓴다. 언급이 없으면 `related` 에 있다는 사실만으로 한 줄을 쓴다. `related` 가 비었으면 섹션을 생략하고 보고에 남긴다.
- **§6** — 한 문장. 페이지에 `육성 인용` 이 있으면 강사가 강조한 어조를 따른다. 꼬리표 줄은 `confidence: high` 이고 `verificationStatus: verified` 인 경우에만 생략한다.

### Step 3: 페이지에 삽입

- 위치는 **본문 마지막 콘텐츠 H2 뒤**, 즉 `## 육성 인용` 이 있으면 그 섹션(딸린 콜아웃 포함) 뒤. 회고성 콜아웃(`Baseline` · `Bias Check` · `Update` · `Contradiction` · `Disputed Claim` · `Exploration Gate`) 과 `## Sources` 는 카드 **뒤**에 남는다. 둘 다 없으면 파일 끝에 붙인다.
- 카드는 페이지에 **직접** 삽입한다. 임시 파일에 써 두었다가 옮기지 않는다 — 병렬 실행 시 공유 scratch 가 서로 덮여 다른 페이지의 카드가 들어간 사례가 있다 (2026-10-07).
- frontmatter 는 `updated` 만 오늘 날짜로 바꾼다. 새 키를 추가하지 않는다.
- 기존 `## Essence Card` 가 있고 `--force` 가 아니면 건드리지 않는다. `--force` 면 기존 카드 H2 부터 다음 H2 또는 회고성 콜아웃 직전까지를 교체한다.
- YAML frontmatter 는 2 스페이스, 본문에 TAB 금지, wikilink 줄은 들여쓰지 않는다 (Obsidian 이 코드 블록으로 읽는다).

### Step 4: 보고

페이지마다 한 줄:

| 페이지 | 결과 | §1 출처 | §2/§4 줄 수 | 생략·주의 |
|---|---|---|---|---|
| {페이지명} | 작성 / 건너뜀(기존 카드) / 재작성 | 복사 / 신규 작성 | 4 / 3 | 예: related 비어 §5 생략 · confidence low 꼬리표 |

MOC 순회 시 건너뛴 non-leaf 항목(Raw Source · 하위 MOC · Entities)은 개수만 적는다.

## Self-Check — 쓰고 나서 페이지와 대조

§3 오류 수정 지시의 확인 순서가 비어 있으면 §4 의 레버를 옮겨 적는다. 카드의 §2 · §3 · §4 각 줄에 대해 "페이지의 어느 줄에서 왔는가" 를 답할 수 없으면 그 줄을 지운다. 지운 뒤 3 줄이 안 되면 그대로 두고 보고에 적는다. 다음은 자주 섞여 드는 바깥 지식이다:

- 페이지에 없는 배치 위치·성능 수치·브라우저/런타임 버전 차이
- 페이지에 없는 오류 메시지 문구 ("X is not defined" 등)
- 페이지가 "피한다" 고만 한 것을 "가장 빠르다" 처럼 **정도**를 더해 쓰기

## Output

보고 표와, 첫 실행이면 작성된 카드 하나를 그대로 보여 준다 (사용자가 형식을 판단할 수 있게).
